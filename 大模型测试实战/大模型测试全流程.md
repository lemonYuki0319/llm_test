# 大模型应用全链路测试体系落地教程
## 一、体系总览
七大模块（模型基准测试、RAG专项测试、业务层应用测试、对话状态与记忆测试、Agent编排测试、安全鲁棒性与性能测试、线上监控）完整覆盖了当前大模型应用测试的核心维度，遵循「自底向上、从组件到系统、从离线到线上」的行业通用逻辑，是扎实的基础框架。

本教程在此基础上，补充每个模块的测试目标、落地步骤、指标细节、工具实操与中小企业轻量化适配方案，形成可直接落地的完整测试流程。

---

## 第1章 模型选型基准测试
### 1.1 测试目标
在项目选型阶段，评估备选大模型的基础能力是否匹配业务底线要求，筛选出性价比最高的接口模型，避免上线后才发现基础能力不足。
> 说明：纯调用第三方接口的中小企业，**不需要做全量学术基准测试**（如MMLU、GSM8K全量数据集），仅需做「业务场景化轻量基准」即可。

### 1.2 核心测试内容
1. **通用能力摸底**：基础语义理解、逻辑推理、格式遵循、中文表达能力，排除明显不符合要求的模型
2. **业务场景小样测试**：用30-50条真实业务高频问题，在完全相同的提示词条件下，对比不同模型的原生输出效果
3. **成本与性能初测**：同一场景下的token消耗量、平均响应速度，结合模型单价核算单请求成本

### 1.3 测试方法
1. 固定统一的系统提示词与用户问题集，保证所有模型测试条件一致
2. 按「事实准确性、语义通顺度、格式合规性」三个维度做分级打分
3. 统计单请求平均token数、响应耗时，结合模型单价计算成本排名

### 1.4 工具选型
- 轻量场景：Excel人工打分 + 接口调试工具（Postman/Apifox）
- 批量评测：OpenCompass（轻量模式）、LM Evaluation Harness
- 中小企业推荐：直接用核心业务问题人工对比，成本最低、决策最准

### 1.5 落地注意事项
- 不要迷信通用榜单排名，业务场景的实际效果比学术基准分更重要
- 优先测试长上下文遵循、格式约束能力，这是中小企业RAG/Agent场景的高频痛点

## 第2章 RAG系统专项测试
### 2.1 测试目标
验证检索环节能否准确召回相关知识，生成环节能否基于检索内容忠实作答，从源头控制幻觉，保障回答的信息准确性。

### 2.2 必跑核心指标
你标注的三个为最高优先级指标，也是RAG项目上线的底线标准：
| 指标 | 指标含义 | 优先级 |
| :--- | :--- | :--- |
| 上下文召回率（Context Recall） | 生成正确回答所需的关键信息点，有多少比例被成功检索到上下文中 | 最高（漏召回必然答错，是底线指标） |
| 答案忠实度（Faithfulness） | 回答内容是否完全基于检索上下文，有无幻觉、无中生有、张冠李戴 | 最高（直接决定系统可信度，是红线指标） |
| 答案相关性（Answer Relevance） | 最终回答是否紧扣用户问题，有无答非所问、冗余跑题、遗漏提问点 | 高（直接影响用户体验） |

可选优化指标：上下文精确率、上下文利用率、引用准确率。

### 2.3 测试方法（基于Ragas框架）
#### 前置准备
1. 构建测试集：整理50-100条核心业务问题，标注对应的「标准答案」和「预期相关的文档片段」
2. 部署可单独调用的RAG测试环境，支持单独获取检索结果、最终回答

#### 执行步骤
1. 将测试集导入Ragas框架，批量调用RAG系统生成回答
2. 框架自动调用裁判大模型，计算三大核心指标得分
3. 提取低分用例，拆解问题归属：
   - 召回率低 → 优化分片策略、检索算法、同义词扩展、重排序模型
   - 忠实度低 → 优化系统提示词、增加引用约束、调整检索TopK数量
   - 相关性低 → 优化提示词聚焦要求、排查检索主题跑偏

### 2.4 工具选型
- 核心框架：Ragas（行业事实标准，指标最全，开箱即用）
- 辅助工具：TruLens Eval（适合链路追踪与问题根因定位）
- 中小企业适配：无需复杂集成，用Ragas官方最简Demo即可跑通核心指标

### 2.5 落地建议
- 测试集优先覆盖高频问题、高风险问题（如售后规则、费用说明、合规条款）
上线前建议阈值：
- 上下文召回率 Context Recall ≥ 85%
- 答案忠实度 Faithfulness ≥ 90%（高危业务如医疗/金融 ≥ 95%）
- 答案相关性 Answer Relevance ≥ 80%（补充）

## 第3章 业务层端到端应用测试
### 3.1 测试目标
站在业务视角验证AI系统的最终输出是否符合产品标准，可直接交付用户/内部员工使用，是上线前的最终验收环节。

### 3.2 测试用例设计
用例来源按优先级排序：
1. **线上真实语料**：从历史客服对话、用户提问记录中提取真实问题，最贴合实际场景
2. **产品业务标准**：基于业务规则、知识库内容，设计边界场景、规则类、异常类用例
3. **鲁棒性补充用例**：同义改写、错别字、口语化表达、模糊提问等异常输入

### 3.3 三层评测方法
#### 方法1：规则匹配校验（关键字/正则表达式）
- 适用场景：有明确标准答案、固定话术、强制输出格式的场景（如退换货规则、固定参数、JSON格式输出）
- 优点：速度快、成本低、100%准确，可全量自动化
- 缺点：只能校验硬性规则，无法判断语义准确性、流畅度
- 落地：提取标准答案中的关键字段、强制话术、格式约束，编写正则/关键字校验脚本

#### 方法2：强模型裁判评分（LLM-as-Judge）
- 适用场景：开放式回答、语义类判断、综合质量评估
- 优点：覆盖语义、逻辑、合规等多维度，适配复杂业务场景
- 缺点：存在裁判偏差，成本高于规则校验
- 落地：将业务评分标准写入提示词，调用能力更强的大模型对输出进行打分；采用「分步推理+最终打分」的提示词结构，降低裁判偏差

#### 方法3：低分/失败用例人工复验
- 适用场景：裁判模型打分低于阈值、规则校验不通过、高风险场景的用例
- 优点：结果最准确，可沉淀bad case反哺测试集与优化迭代
- 缺点：人力成本高，无法全量覆盖
- 落地：设置评分阈值（如低于60分），自动归集失败用例，由测试/产品人工复核，确认问题后提交优化

### 3.4 工具选型
- 核心框架：DeepEval（原生支持多维度评测、自定义评分标准，适合业务层端到端测试）
- 轻量方案：Python脚本 + 正则匹配 + 大模型接口调用
- 中小企业适配：核心规则场景用自动化，语义场景用强模型抽测，高风险场景人工复核

### 3.5 落地流程
1. 梳理业务验收标准，拆分「规则强制项」和「语义质量项」
2. 设计测试用例集，标注对应验收标准
3. 批量调用AI流式接口，先跑规则校验，再跑强模型评分
4. 自动归集失败与低分给例，人工复核确认问题
5. 输出测试报告，跟踪问题闭环

## 第4章 对话状态与记忆系统测试
### 4.1 测试目标
保障多轮对话场景下，系统能正确理解上下文、管理用户记忆，避免多轮后信息丢失、记忆混乱、跨用户数据泄露。

### 4.2 两大测试模块
#### 模块一：上下文窗口测试（单次对话内的临时记忆）
上下文是单轮对话窗口内的临时信息，分为短上下文（3-5轮）和长上下文（几十轮以上），核心测试点：
1. **信息定位能力**：多轮对话中提到的细节信息，后续提问能否准确提取
2. **上下文保持能力**：多轮对话后，核心主题、用户身份、前置约定是否保持一致，不会前后矛盾
3. **长上下文召回**：长对话中，早期提到的信息能否被准确定位（验证长上下文窗口的尾部遗忘问题）
4. **窗口边界处理**：对话长度接近上下文窗口上限时，截断逻辑是否合理，不会出现关键信息丢失、输出异常

#### 模块二：持久化记忆测试（跨对话的长期存储）
记忆是持久化存储的用户信息（如用户偏好、历史订单、个人标签），核心测试点：
1. **读写正确性**：系统能否正确提取用户信息存入记忆，调用时能否准确读取
2. **用户隔离性**：不同用户的记忆数据是否完全隔离，不会出现A用户的记忆串到B用户（数据安全红线指标）
3. **记忆更新能力**：用户信息变更后，记忆能否正确更新覆盖，不会新旧信息冲突
4. **记忆遗忘/过期**：超出有效期的记忆能否自动清理，无效记忆不会干扰对话
5. **敏感信息过滤**：用户输入的身份证、手机号等敏感信息，是否会被过滤，不会存入记忆

### 4.3 测试方法
1. 按场景构造多轮对话测试集，设计上下文关联、记忆读写的验证点
2. 编写自动化脚本，模拟多轮对话流程，逐轮校验输出内容
3. 输出结果校验复用业务层的三层评测方法（规则匹配+强模型+人工复核）

### 4.4 工具选型
- 自动化脚本：基于Python + DeepEval扩展多轮对话评测
- 链路追踪：LangSmith（可查看每轮的上下文与记忆调用情况）
- 中小企业适配：优先测记忆隔离、核心上下文保持，长上下文测试按需补充

## 第5章 Agent编排与工具调用测试
### 5.1 测试目标
验证Agent的决策逻辑与工具调用行为符合预期，流程节点流转正确，外部接口调用稳定，避免决策错误、工具乱调、流程卡死。

### 5.2 核心测试维度
#### 1. 流程节点正确性
- 验证Agent流程图的每个分支、节点能否按预设逻辑触发，边界条件下的分支跳转是否正确
- 异常场景（如工具调用失败）的兜底、重试、降级逻辑是否生效

#### 2. 工具选择与调用准确性
- 工具选择：用户提问对应正确的工具，不会选错工具（如查天气选了查订单）
- 参数传递：调用工具时，提取的参数是否准确、完整，格式符合接口要求
- 结果使用：工具返回的结果，能否被Agent正确理解并用于生成回答

#### 3. MCP/Skill与外部接口调用测试
- 接口可用性：外部API、MCP工具的调用成功率、返回格式兼容性
- 异常容错：接口超时、报错、返回空值时，Agent能否正常处理，不会崩溃或输出异常
- 权限控制：涉及数据读写的工具，权限校验是否生效，不会越权操作

#### 4. 决策逻辑合理性
- 什么时候调用工具、什么时候直接回答，决策是否符合业务规则
- 多工具组合调用时，执行顺序、依赖关系是否正确

### 5.3 测试方法
1. **流程图覆盖法**：基于Agent的业务流程图，设计用例覆盖所有节点、分支、异常路径
2. **端到端场景验证**：构造真实业务场景的用户提问，验证全链路决策与输出是否符合预期
3. **异常注入测试**：模拟工具超时、返回错误、参数缺失等异常，验证兜底逻辑

### 5.4 工具选型
- 链路追踪：LangSmith（可完整查看Agent的思考过程、工具调用步骤、参数传递，是Agent调试测试的核心工具）
- 自动化测试：自定义Python脚本，结合DeepEval做行为校验
- 中小企业适配：简单工具调用Agent，优先测工具选择准确率、参数正确性；复杂编排再测全流程分支

## 第6章 安全鲁棒性与性能测试
### 6.1 安全鲁棒性测试
#### 测试目标
防范内容违规、Prompt注入攻击、数据泄露、越狱等安全风险，保障系统合规运行。安全风险没有企业规模豁免权，反而是中小企业抗风险能力更弱，更需要守住底线。

#### 核心测试维度
1. **内容合规测试**：验证系统不会输出涉政、色情、暴力、违法等违规内容
2. **Prompt注入测试**：测试用户能否通过诱导指令绕过系统提示词，执行恶意指令、窃取系统提示/知识库内容
3. **敏感数据泄露测试**：验证系统不会泄露内部知识库敏感信息、用户隐私数据
4. **鲁棒性测试**：同义改写、错别字、模糊提问、超长输入等异常场景下，输出效果是否稳定
5. **对抗性测试**：诱导越狱、角色扮演绕过等高级攻击场景（中小企业可简化）

#### 测试方法
1. 采用开源安全数据集 + 自定义业务攻击用例，批量跑测
2. 结合内容安全接口做违规检测，人工复核可疑case
3. 工具：Garak（安全攻防测试）、PromptFoo（Prompt注入与鲁棒性测试）、DeepEval安全评测模块

### 6.2 性能压测
#### 测试目标
验证系统在业务峰值下的响应速度、稳定性与资源占用，保障用户体验，同时核算容量与成本。

#### 核心性能指标
| 指标 | 全称 | 含义 |
| :--- | :--- | :--- |
| TTFT | Time To First Token | 首Token响应时间，用户感知最明显的指标 |
| TPOT | Time Per Output Token | 首 token 之后、每个后续 token 的平均间隔 |
| P95/P99 延迟 | - | 95%/99%请求的总耗时，衡量整体体验底线 |
| TPS | Tokens Per Second | 每秒可处理的Token数，衡量系统吞吐量 |
| QPS/RPS | Queries/Requests Per Second | 每秒处理的请求数，衡量系统并发吞吐量 |
| 错误率 | - | 请求超时、报错的比例 |
| 资源占用 | - | GPU/CPU/内存使用率（自部署场景） |
| 单任务Token成本 | - | 完成一个业务任务的总token消耗与费用（Agent/RAG多步调用尤其重要） |

#### 测试方法
1. 梯度加压：从低并发逐步提升到业务峰值的2倍，观察指标变化
2. 稳定性压测：业务峰值压力下持续运行30分钟以上，验证无内存泄漏、错误率稳定
3. 极限测试：逐步加压到系统瓶颈，找到最大承载量

#### 工具选型
- 大模型专属压测：Guidellm（专门针对大模型接口设计，原生支持TTFT、TPOT等指标）
- 通用压测：Locust、wrk（适合全链路压测）
- 中小企业适配：压测到业务预估峰值的2倍即可，无需极限压测

## 第7章 线上监控与持续迭代
### 7.1 测试目标
线上运行阶段持续收集bad case，定期做效果回归，驱动系统持续优化，形成「测试-上线-监控-优化」的闭环。

### 7.2 核心监控内容
#### 1. 效果质量监控
- 核心指标：幻觉率、答非所问率、违规内容率、用户差评率
- 采集方式：用户点赞/点踩反馈、定期抽样离线评测、关键词自动拦截bad case

#### 2. 性能可用性监控
- 核心指标：接口错误率、平均耗时、TTFT、限流触发次数
- 责任边界：业务侧监控接口层指标，GPU、服务器等基础设施监控由运维负责

#### 3. Bad Case 闭环流程
1. 线上日志、用户反馈、告警自动归集bad case
2. 每周定期整理bad case，补充到离线测试集
3. 跑全量回归测试，验证优化效果，避免问题复现
4. 沉淀典型问题，反哺知识库、提示词、检索策略优化

### 7.3 工具选型
- 核心工具：LangSmith（原生支持大模型链路追踪、效果统计、bad case标注，是行业主流选择）
- 日志监控：ELK、企业现有日志系统
- 中小企业适配：不用搭建复杂可观测平台，用LangSmith免费版+每周人工复盘bad case即可满足需求

## 第8章 中小企业阶段化落地路线
不用一步到位全量覆盖，按三个阶段逐步落地：
### 阶段一：MVP上线前（基础准入）
- 必做：模型选型对比、RAG三大核心指标测试、核心业务场景端到端测试、基础安全合规测试
- 目标：保障核心场景可用，无严重幻觉、合规风险

### 阶段二：正式上线前（全面验证）
- 补充：对话上下文与记忆测试、Agent工具调用测试、性能压测、鲁棒性测试
- 目标：覆盖主要业务场景，系统稳定可控，可面向全量用户开放

### 阶段三：线上运营期（持续优化）
- 落地：线上监控体系搭建、定期回归测试、bad case闭环迭代
- 目标：持续提升效果，控制成本，快速响应线上问题

## 附录：优化后的LLM-as-Judge评测提示词模板
针对业务层评测的通用提示词做了严谨化优化，增加分步推理要求，减少裁判主观偏差，提升打分一致性。

### 通用业务回答质量评分提示词
```
你是一名专业的AI输出质量评测员，请根据以下评分标准，对AI助手的回答进行客观公正的评分。

【评分标准】
满分100分，从以下4个维度加权打分：
1. 事实准确性（40分）：回答内容完全符合业务规则与给定参考知识，无事实错误、无编造信息、无张冠李戴
2. 问题相关性（30分）：回答紧扣用户问题核心诉求，无答非所问、无冗余无关内容，覆盖所有提问点
3. 表达合规性（20分）：语句通顺、逻辑清晰，符合业务话术规范，无违规内容
4. 格式正确性（10分）：符合要求的输出格式（如列表、JSON、固定模板等），无格式混乱

【输入信息】
用户问题：{{user_query}}
业务参考知识：{{reference_context}}
AI助手回答：{{ai_answer}}

【输出要求】
1. 先分步分析每个维度的得分与理由，必须结合回答内容具体说明扣分点
2. 最后给出最终总分，格式为：最终得分：X分

请严格基于给定的参考知识判断，不要引入外部知识，也不要受回答语气的影响，只判断内容本身的质量。
```

### 幻觉专项检测提示词（Faithfulness校验）
```
你是一名事实一致性检测员，请判断AI回答中的每一个事实论断，是否都能在参考上下文中找到明确依据。

【参考上下文】
{{reference_context}}

【AI回答】
{{ai_answer}}

【执行步骤】
1. 将AI回答拆解为若干个独立的事实论断
2. 逐一比对每个论断是否能在参考上下文中找到原文依据
3. 统计有依据的论断数量与总论断数量

【输出格式】
总论断数：X
有依据论断数：Y
是否存在幻觉：是/否
详细说明：逐条列出无依据的论断内容
```
