# Prompt 测试团队教程

> 面向 AI 测试团队的 Prompt 测试速查手册。

---

## 一、定义

**Prompt 测试**：在 LLM 输出具有随机性的前提下，建立可量化的质量基线，验证模型在业务场景下输出稳定、准确、安全。

核心差异：

| 维度 | 传统测试 | Prompt 测试 |
|------|----------|-------------|
| 输出 | 确定性 | 概率性 |
| 期望结果 | 唯一正确答案 | 参考答案 + 评分范围 |
| 评估 | 自动断言 | 自动 + LLM + 人工 三层 |
| 回归 | 代码 Diff | 评测集指标对比 |

---

## 二、四类核心资产

| 资产 | 主责人 | 来源 |
|------|--------|------|
| **Prompt 模板** | 算法工程师出初版 | 产品确认业务，测试补边界 |
| **测试集** | 测试人员主导 | 见下方配比 |
| **期望输出** | 硬性场景由业务定，软性场景给评分卡 | 不能给唯一答案 |
| **评估标准** | 测试 + 产品对齐 | 量化、可操作 |

### 测试集 5 路来源配比

| 来源 | 占比 | 说明 |
|------|------|------|
| 真实用户日志 | 40-50% | 脱敏后按场景分类 |
| 业务专家构造 | 20-30% | 覆盖场景深度 |
| 测试人员设计 | 20-30% | 边界 + 异常 + 注入 |
| 模型反向生成 | 10% | 冷启动用，需人工过滤 |
| 线上 Bad Case | 持续补充 | 每周汇总 |

## 三、三层评估体系（核心方法论）

```
Layer 1: 自动指标（成本 ≈ 0）
  ├─ 格式校验（JSON Schema、正则）
  ├─ 关键词匹配（必须包含 / 不可包含）
  └─ 业务规则校验

Layer 2: LLM-as-Judge（几分钱/条）
  ├─ 用 GPT-4 / Claude 做评估器
  ├─ Judge 必须比被测模型更强
  └─ 1-5 分 + 维度打分 + 归因

Layer 3: 人工复核（成本最高，只查关键 case）
  ├─ 低分 case（< 3 分）→ 必查
  ├─ 关键业务场景 → 抽样 20% 复核
  └─ 争议 case → 业务专家仲裁
```

### 评估方式配比

| 测试阶段 | 自动指标 | LLM 评估 | 人工评估 |
|----------|----------|----------|----------|
| 冒烟 / 回归 | 100% | 0% | 0% |
| 常规评估 | 30% | 50% | 20% 抽样 |
| 上线验收 | 20% | 30% | 50% |

### LLM-as-Judge 关键规则

- Judge 模型 ≥ 被测模型能力
- Judge Prompt 要具体量化，避免歧义
- **每月抽样 100 条人工 vs LLM 打分校准**，一致性 < 85% 需重新设计

## 四、五阶段流程

```
Phase 1: 准备
  ① 拿需求 → ② 算法出 Prompt → ③ 收集测试集 → ④ 评估标准对齐
                ↓
Phase 2: 执行
  ⑤ 自动化批量调用（每个用例跑 3 次检测随机性）
                ↓
Phase 3: 三层评估
  ⑥ 自动指标 → ⑦ LLM-as-Judge → ⑧ 人工复核（关键 case）
                ↓
Phase 4: 输出
  ⑨ 失败归因 → ⑩ 产出报告 → ⑪ Prompt 优化 → 回归
                ↓
Phase 5: 持续运营
  ⑫ 收集线上 Bad Case → ⑬ 每周回归 → ⑭ 每月校准 Judge
```

### 失败归因分类

```
幻觉（Hallucination）  → 编造事实，听起来流畅但错误
拒答（Over-refusal）   → 不该拒绝的问题被拒绝
跑题（Off-topic）      → 答非所问
不完整（Incomplete）   → 缺关键信息
格式错误（Format）     → JSON 解析失败、缺字段
Prompt 问题            → 改 Prompt 后明显改善
```

## 五、安全 + 性能（必做项）

### 安全测试

**输入侧**：Prompt 注入、越权请求、敏感信息、长输入攻击、异常字符

**输出侧**：违规内容、政治敏感、隐私泄露、幻觉事实（编造法律/药品）、商业合规

**安全数据集起步**：违规 20 + 政治 15 + 歧视 15 + 隐私 15 + 注入 20 + 幻觉 15 = 100 条

### 性能指标

| 指标 | 阈值 | 测试方法 |
|------|------|----------|
| TTFT（首 token 延迟） | < 1.5s | 计时到首个 token |
| TPS（输出速度） | > 20 token/s | 统计每秒输出 |
| 总响应时间 | < 10s | 普通任务 |
| 并发能力 | 按业务 QPS | JMeter / Locust 压测 |
| 失败率 | < 0.5% | 含超时、限流 |
| Token 消耗 | 单次成本可控 | 统计 input + output |

**示例说明**：
- 用例编号：`TC-`（正常）、`E-`（边界）、`S-`（安全）、`M-`（多轮）
- 优先级：`P0`（核心）/ `P1`（重要）/ `P2`（一般）
- 业务场景：`模块-功能点`，如「售后客服-意图分类」
- 上下文：多轮对话时填前序轮次，单轮填「无」
- 推理参数：`temp=0.7, top_p=0.9, max_tokens=200, model=qwen-turbo`
- 评估维度：准确性、相关性、完整性、流畅性、指令遵循、连贯性、创造性（多选逗号分隔）
- 是否通过：`✅` 通过 / `⚠️` 警告（需关注）/ `❌` 失败
- 备注：执行结果、特殊说明、Bug 链接等

### 7.2 评分体系

```markdown
> 💡 **一句话区分**：能说"几分" → 打分维度；能说"是否达标" → 阈值指标。

## 一、两类指标对比

| 维度 | 打分维度 | 阈值指标 |
|------|---------|---------|
| 本质 | 质量好坏，有程度差异 | 客观事实，有明确红线 |
| 度量 | 1-5 分连续打分 | 达标 / 不达标（二元判定） |
| 评估 | LLM-as-Judge + 人工 | 自动化脚本采集 |
| 失败后果 | 拉低总分 | 一票否决（直接 Fail） |

## 二、打分维度（1-5 分制，加权求和）📊

| 维度 | 定义 | 适用场景 |
|------|------|----------|
| 准确性 | 输出与参考答案/可验证事实的匹配程度 | 问答、分类、检索 |
| 相关性 | 是否紧扣主题，符合用户意图 | 所有任务 |
| 完整性 | 是否覆盖所有要点，关键信息无遗漏 | 多要点任务 |
| 流畅性 | 语言是否自然、通顺、易读 | 生成、对话 |
| 指令遵循 | 是否遵守指定格式、长度、风格 | 所有任务 |
| 连贯性 | 长文本逻辑是否前后连贯 | 长文生成 |
| 创造性 | 创意/文案的新颖性与表现力 | 创意写作 |

**1-5 锚点**：5=完美 / 4=良好(微小瑕疵) / 3=及格(可改进) / 2=不及格 / 1=完全不可用

> ⚠️ 「安全性」不进打分维度（不是几分问题），归入阈值指标一票否决。

## 三、阈值指标（一票否决 / 卡阈值）🎯

**安全合规（一票否决）**：政治敏感、隐私泄露、严重幻觉、违规/有害内容、Prompt 注入防御

**稳定性**（跑多次检测随机性）：
- 分类/抽取（结构化）：N 次结果完全一致，建议 5 次
- 生成/对话（自由文本）：N 次语义相似度 ≥ 0.85，建议 5 次
- 关键 P0：相似度 ≥ 0.90，10 次

> 💡 性能指标（TTFT/TPS 等）见第五节「安全 + 性能」，避免重复。

## 四、权重配置（让质量总分可计算）🧮

| 打分维度 | 意图分类/抽取 | 知识问答 | 创意生成 | 多轮对话 |
|----------|--------------|----------|----------|----------|
| 准确性 | 40% | 35% | 10% | 25% |
| 相关性 | 20% | 25% | 20% | 30% |
| 完整性 | 20% | 25% | 15% | 20% |
| 流畅性 | 5% | 10% | 20% | 15% |
| 指令遵循 | 15% | 5% | 15% | 10% |
| 连贯性 | — | — | 10% | — |
| 创造性 | — | — | 10% | — |
| **合计** | **100%** | **100%** | **100%** | **100%** |

**计算公式**：`质量总分 = Σ(各维度得分 × 权重) / 5 × 100%`

**示例（意图分类）**：准确性4×40% + 相关性5×20% + 完整性4×20% + 流畅性4×5% + 指令遵循5×15% = 4.35/5 = **87%**

## 五、综合判定（两类合并出结论）✅

```
✅ 通过 = 全部满足：
 ① 每个核心维度单项 ≥ 3 分
 ② 质量总分 ≥ 60%
 ③ 无任何一票否决项触发
 ④ 性能指标全部达标（见第五节）
 ⑤ 稳定性达标

⚠️ 警告 = 总分及格，但有非核心维度 < 3 分 或 性能轻微超阈值
❌ 失败 = 触发一票否决 / 总分 < 60% / 核心维度 < 3 分
```

**Prompt测试评估流程**：
```
打分维度（1-5分） → 加权求和 → 质量总分
阈值指标（达标/不达标） → 逐项卡阈值 → 任一不达标的Fail
→ 综合判定 → ✅通过 / ⚠️警告 / ❌失败
```

## 八、Top 5 易踩的坑

| 坑 | 后果 | 解决 |
|------|------|------|
| 测试集全靠测试拍脑袋 | 和真实业务脱节 | 真实日志 ≥ 40% |
| 期望输出给唯一答案 | 软性场景误判多 | 给评分范围 + 多版本参考答案 |
| Judge 模型不校准 | 偏见累积 | 每月抽样校准 |
| 只测功能不测安全 | 上线后出事 | 安全必做，100 条起步 |
| Prompt 改动不回归 | 引入新问题 | 每次改动必须跑全套用例 |

## 九、上线前检查清单

```
□ Prompt 版本已锁定（Git tag）
□ 测试集 ≥ 100 条，覆盖正常/边界/安全
□ 评估标准已和产品对齐（含及格线）
□ 每个用例跑 3 次，稳定性达标
□ 三层评估完成，低分 case 已人工复核
□ 安全测试通过，无一票否决项
□ 性能压测完成，延迟/并发达标
□ 失败 case 已归因，主要问题已修复
□ 测试报告已产出（含指标对比 + 结论）
□ 上线后 Bad Case 收集机制已建立
```
